Nullecho — blocking proof

Positive proof that the network-blocking layer blocks, not just that the extension loads.

Read before you run. This page requests real tracker script URLs. With Nullecho on, they should be cancelled and never leave your machine — that is the whole point of the test. With Nullecho off, they do reach Google, Meta and the others as ordinary CDN script fetches.

Every tracker URL below is a static library file, never an event beacon (analytics.js, not /collect) — running this does not record a page view, a conversion, or a click anywhere.

What this can and cannot tell you

It can prove: requests to tracker hosts are being cancelled while ordinary requests still succeed. That is the difference between "the extension runs" and "the extension works."

It cannot prove: who cancelled them. A no-cors fetch rejects identically for a blocked request, a DNS failure and a dead network. That is what the control rows are for — if the controls load and the trackers do not, something is deliberately cancelling trackers. If nothing loads, you are offline and the run is void, which this page says out loud rather than scoring as a pass.

The two checks this page can't do for you

  1. The popup counter agrees. With this page still open, open the Nullecho popup. It should show a non-zero blocked count for this page. If this page says trackers were blocked and the popup says zero, the counting path is broken even though blocking works — that is a real bug, and this is the only place it shows up.
  2. GPC suppression on an excepted host. This page reports navigator.globalPrivacyControl below; here it should be true. Then open https://open.spotify.com — a shipped GPC exception — and run navigator.globalPrivacyControl in its console. It must be undefined there. Those two readings together prove the exception mechanism; see docs/BREAKAGE-TESTING.md Tier C.15 for why proving the mechanism twice beats visiting fifty sites once.
