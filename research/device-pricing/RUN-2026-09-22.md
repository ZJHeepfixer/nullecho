# Device-price probe — run of 2026-09-22

Instrument `harness/device-price-probe.mjs` · sites `harness/device-price-sites.json` · raw per-load data
`raw/2026-09-22.json` · method, controls and limits in `METHOD.md` (read it before quoting anything below).

**The finding, stated plainly:** seventeen public pages, four device profiles, twelve interleaved loads
each, one connection, one afternoon. **No page showed a device-based price difference that survived
inspection.** Nine pages declared the same price to all four devices on every load. Eight could not be
measured cleanly (bot walls, phone templates with no declared price, a price that drifted within a single
device, one HTTP/2 error on phone profiles). The one result the instrument first labelled "differs by
device" was the instrument's own error: a page listing many models, read as its first offer. It is
reclassified below and the probe was changed afterwards.

## What this run does NOT show

- **A device difference is not proof of personal-data pricing.** Every visitor here was anonymous: no
  account, no cookie, no history. A site can quote by device class for reasons that involve no
  personal data (a mobile-only promotion, a different fee bundle, a different default variant).
- **One connection, one day, one region.** One residential connection in one US state, 13:58–14:39
  Pacific on 2026-09-22. Nothing here generalises to another IP, another state, another week.
- **Anonymous visitors only.** Logged-in, loyalty, cart and checkout pricing were not tested — and are
  where personalisation would most plausibly live.
- **A price declared in markup may differ from what a person sees.** JSON-LD / meta prices are written
  for search engines; they are often right, sometimes stale, sometimes a base variant's. Where a
  visible-text selector was used (flagged `visible`) the number is what rendered, parsed from text.
- **A/B experiments exist.** The same-device repeat check catches a bucket that flips inside our 12
  loads; it cannot catch one assigned once per connection.
- **Mobile sites may quote different fees or bundles.** A lower declared base price on a phone page
  can mean fees folded differently, not a lower total.
- **The engine under every profile is Chromium.** The "iPhone Safari" row is Chromium wearing Safari's
  UA, viewport and touch; consistent on the wire, but JavaScript feature-detection sees Chromium.
- **Automation is visible.** `navigator.webdriver` was true on every load. A site that quietly changed
  its behaviour for suspected automation would look identical to one that did nothing.

`same` below means "did not vary, for these four devices, in these 12 loads, at this hour" — not
"never varies". `blocked` and `inconclusive` mean exactly that, and are not evidence either way.

## The reclassified result, in full

Apple's "Buy iPad" page carries one JSON-LD `Offer` per iPad model. The extractor took the first offer.
The desktop template listed a $599 model first (a $699 model first on the +10-minute recheck); the phone
template listed a $549 model first, on every load. Read as one price, that is "desktop 599–699, phone
549" — three consistent loads per device, two devices differing, exactly the shape the verdict logic
calls "differs by device". Read as the set of offers each load declared, all four devices carried the
same models at the same prices (449 / 549 / 599 / 699 / 749 / 899 USD), with a single model missing from
some desktop loads. Nothing in this points to a device-based price; it points to two templates ordering
the same catalogue differently.

Two consequences. (1) The result is `inconclusive: multi-offer page` for this run, and this document says
so rather than quietly dropping the row. (2) The probe now compares the sorted set of distinct JSON-LD
prices whenever a page declares more than one (`json-ld-set(N)`), so a catalogue page can no longer
produce a device claim from its first offer. The raw JSON for this run is from the earlier extractor; the
reclassification above was done by hand from the `allJsonLdPrices` recorded on every load.

## The walls, verbatim

- Walmart: "robot or human" interstitial on the second round for three profiles (the fourth profile's
  second load never ran; the site was abandoned after three consecutive blocked loads, per method).
- SeatGeek: HTTP 403 on the first load of every profile.
- Dell: HTTP 403 "access denied" for the Mac desktop profile on all three loads and for the Windows
  profile once; the two phone profiles were served normally.
- Best Buy: `net::ERR_HTTP2_PROTOCOL_ERROR` for both phone profiles on all six loads; both desktop
  profiles were served normally.
- Airbnb: one HTTP 429 (android-budget, round 3).

## What we would say in public, and what we would not

Say: "On 2026-09-22 we loaded seventeen public product, travel and ticket pages as four different
devices from one connection. Nine showed the same declared price to every device. Eight could not be
measured cleanly. None showed a device-based difference we could stand behind, and the one that looked
like it was our own instrument reading a catalogue page wrong."

Do not say: anything about "discrimination", anything about any site's intent, anything that
generalises beyond one afternoon and one connection, or anything about the eight pages the instrument
could not read.
