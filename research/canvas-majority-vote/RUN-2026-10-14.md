# Canvas majority-vote attack against Nullecho — run of 2026-10-14

**Question.** Does the attack that broke Brave's canvas farbling in 2025 also recover the real
canvas through Nullecho's canvas noise? Our "50 reads → 1 hash" result only covers repeated reads of
one canvas, and three of our documents described the 2025 attack as per-read averaging (erratum E10
in the counter-program's B-COUNTERMEASURES-EVIDENCE.md).

**Answer.** Yes. With 21 canvases and a plurality vote the real canvas came back exactly in **60 of 60**
trials from the source tree and **27 of 28** from the store zip (the one miss was a single channel). It
was **byte-identical under two personas on two sites**, which restores the cross-site join for the
canvas signal. The attack took medians of 0.15–0.5 s, depending on machine load. No deterministic
noise kernel we prototyped
survives both this vote family and the A1 uniform-fill subtraction. So nothing is shipped as a
mitigation, the kernel is unchanged, and the claims are qualified instead (DECISIONS.md D56).

## Source

Hoang Dai Nguyen and Phani Vadrevu, *Breaking the Shield: Analyzing and Attacking Canvas
Fingerprinting Defenses in the Wild*, WWW '25, pp. 4337–4344, doi:10.1145/3696410.3714713, CC BY 4.0
(https://www.phanivadrevu.com/files/papers/canvas_fp.pdf, read in full).

§7.2 and Algorithm 3, "The Statistical Attack":
1. Draw the same content on five 500×400 "Filled Canvases".
2. Add a 500×10 rectangle of a unique colour to the top of each.
3. Read the region excluding the rectangle with `getImageData()`.
4. For each pixel and each of R, G and B, take the value that appears in at least 3 of the 5 reads.

Why it works on Brave: Brave keys its noise on a session key, the domain and the canvas content
(their Algorithm 2). Each strip colour therefore gets a fresh noise selection. Brave flips at most
256 single-channel LSBs, so a per-channel majority over 4–5 canvases is enough.

Nullecho (`shim.js` `noiseRGBA`, D22) keys its noise on the persona key, the canvas size, a digest of
the whole canvas and the position. It changes about 1 pixel in 8, by ±1 or ±2 on R, G and B.

## Method

`harness/canvas-majority-vote.mjs` drives `harness/canvas-majority-vote.html`. The page's attack code
never sees the truth; only its scoring code does.

**Environment.** Chrome for Testing 149.0.7827.22, headless, Puppeteer 25.1.0, this Mac. Pages were
served on `http://alpha.test` and `http://bravo.test`, both mapped to loopback with
`--host-resolver-rules`, so nothing left the machine. Raw results:
- [`run-2026-10-14.json`](run-2026-10-14.json): commit `94c72da`, clean `ext/` and `harness/`, a
  copy of `ext/` loaded unpacked.
- [`run-2026-10-14-package.json`](run-2026-10-14-package.json): the same commit, testing the store
  zip that `ext/tools/package.mjs` built (sha256 `03ec1422…`).

Both runs predate the rebase onto main `88fd0e4`; `94c72da` is `27ca2c7` after the rebase. That
rebase brought only `ext/options/drop.html` and `site/` changes, and `shim.js` and the harness are
byte-identical.

A confirmation run on the store zip built from the rebased branch is in
[`run-2026-10-15-package-postrebase.json`](run-2026-10-15-package-postrebase.json) (commit `00b1396`,
zip sha256 `e09f9109…`, N = 21 only). Results:
- plurality exact in **12/12** CPU-backed and **4/4** default-canvas trials;
- one recovered hash across all four cells;
- translate 12/12; A1 fails; the Worker read equals the truth;
- all controls passed;
- medians of 152–168 ms (CPU-backed) and 236–250 ms (default).

**Canvas.** 500×410: the 500×400 fingerprint region, with the strip above it. That keeps the
paper's 800,000 numbers per read.

The content is an opaque "Filled Canvas" and includes:
- a linear gradient;
- text in Arial, Times New Roman and Georgia italic, with two emoji;
- three arcs blended with `multiply`;
- a shadowed Bézier curve and a partial disc.

**The port.** Algorithm 3 is followed as written, with two choices the paper leaves open:
- Where no value reaches a strict majority, F1's value is kept.
- Alpha is copied from F1. The paper votes R, G and B only, and Nullecho never changes alpha.

The plurality vote (most frequent value; ties go to F1's value, else the smallest) is our extension
of the paper, as the brief asked.

**Grid.**
- Canvas counts: N = 5, 9 and 21.
- Votes: strict majority and plurality.
- Two personas: two fresh profiles, so two independently generated salts (salt tags `b36f7cbf` and
  `70938b6b`).
- Two origins.
- Trials: 10 per cell with CPU-backed canvases, and 5 per cell with Chrome's default canvases (one
  fresh page per trial).

**Ground truth.** The same page in a Chrome with **no extension**, read once per origin.

**Context mode (a measurement-environment finding).** Chrome renders GPU-backed and CPU-backed 2D
canvases differently (24,435 of 200,000 pixels here). It also **switches a document's new canvases**
to the other backing after roughly 200 `getImageData` calls. The first full run crossed that switch
partway through and recorded N = 21 as 0/40. That was wrong, and the isolated-world truth check
below is what caught it. The page therefore offers two context modes:
- **Default:** every canvas is CPU-backed (`willReadFrequently`). That is the attacker's own choice,
  and its backing never switches.
- **`?ctx=default`:** Chrome's default canvases, the paper's setting. Each trial gets a fresh page, so
  a run never reaches the switch.

Each mode has its own truth: `555d6de0…` (CPU) and `3c599fef…` (default).

**The store zip** (5 CPU + 2 default trials per cell):
- N = 21 plurality: **19/20** CPU (the miss: 1 channel) and **8/8** default.
- N = 5 and N = 9: 0, as above.

**The cross-site join.** Every exact recovery across both personas and both sites produced one hash
per canvas mode (`555d6de0…` and `3c599fef…`). Single reads, by contrast, gave four different hashes.

**Variants on the real extension.**
- *Translate*: the same region blitted at 21 different integer offsets. Recovered 20/20 at N = 21
  (0/20 at N = 9).
- *A1 uniform-fill subtraction*: fails in every cell (137,722–138,447 channels wrong).
- *Worker (gap G1)*: the fingerprint on an `OffscreenCanvas` in a dedicated Worker. One read returns
  bytes **identical to the extension-OFF truth** in all four cells. No attack is needed.

**Timing variance.** An earlier complete run (`2026-10-14`, same code, less machine load) measured
the N = 21 plurality attack at a median of 143 ms in two of the four cells. Across runs, the vote
alone took 78–234 ms.

**The paper versus us.** The paper's N = 5 does *not* recover our canvas exactly. Our denser
1-in-8 noise leaves about 2,100 pixels wrong at N = 5. Brave changes at most 256 pixels, so N = 5
suffices there. Our noise moves the attacker's cost from 5 canvases to about 21 (≈ 0.1 s → ≈ 0.5 s).
That is a cost, not a defense.

## Mitigation prototypes

Each prototype is an in-page kernel installed on `getImageData` with the extension off. The prototypes
reuse the shipped `fin32`/`prf`/`keyMix`/`noiseRGBA` functions, extracted from `shim.js` text at run
time, and the same ±1/±2, 1-in-8 perturbation rule. The table shows exact recoveries over 10 trials
(5 per key × 2 keys) with the plurality vote; the strict-majority count is in brackets.

| Kernel: noise keyed on | Single read, px wrong | Strip N = 21 (Algorithm 3) | Translate N = 21 | Colour-shift N = 21 | 21 documents | A1 subtraction |
|---|---|---|---|---|---|---|
| **shipped (D22)**: persona, size, whole-canvas digest, position | ≈ 25,100 | **10/10 (1)** | **10/10 (3)** | **10/10 (4)** | — | fails |
| pre-D22: persona, size, position | ≈ 25,000 | 0/10 | not run | not run | — | **recovers** (all but 577 clamp-lost channels) |
| *pos-value*: persona, position, the pixel's own value | ≈ 25,000 | 0/10 | **10/10 (3)** | **10/10 (3)** | — | fails |
| *tile16*: persona, digest of its 16×16 tile, position | ≈ 25,000 | 0/10 (only the rows sharing a tile with the strip recover) | **10/10 (2)** | not run | — | fails |
| *value-lut*: persona, the pixel's own value only | 11,955 / 5,341 | 0/10 | 0/10 | **10/10 (10)** | — | fails |
| *budget2*: shipped, plus 2 distinct canvases per document between trusted user gestures, then blank | ≈ 25,100 | 0/10 (blanked) | — | — | **10/10 (1)** | blank |
| Brave-shaped (positive control) | 111 / 134 | 10/10 (10) | 10/10 (10) | — | — | fails (adds ≈ 250 flips) |

*Translate* blits the region at 21 integer offsets; `drawImage` between canvases is exact, as
verified with the extension off.

*Colour-shift* composites a solid colour c_i over each copy with `difference` on a CPU-backed canvas,
which is exact; on a GPU-backed canvas it was off by up to 2 on 576 channels. The attacker undoes
each shift using the side read off one plain noised copy, and votes.

*21 documents* puts one canvas in each of 21 same-origin iframes. Each iframe is a fresh document,
so it gets a fresh budget.

Reading the table:
- Every kernel that defeats the literal Algorithm 3 does so by keeping the noise the same for the
  same pixel. The attacker then varies the next thing the kernel keys on:
  - *tile16* and *pos-value* key on position and fall to translation;
  - *value-lut* keys on the pixel value and falls to the colour shift.
- The only kernel immune to every variation is one keyed on nothing the attacker can't reproduce,
  and that is the pre-D22 kernel A1 subtracts away.
- A per-document read budget, which is all a MAIN-world shim can enforce synchronously, falls to more
  documents.
- The Worker path reads the truth whatever the main thread does.

## Attacking our own work

- **Positive controls passed** (Brave-shaped noise for the vote, the pre-D22 kernel for A1) before any
  negative result was trusted.
- **Planted break, unit level.** With `canvasKeyFor` reverted to the pre-D22 position-only key, all
  three D56 tests go red.
- **Planted break, real extension.** The same reverted `shim.js` was loaded as the extension
  (3 CPU + 1 default trials per cell, N = 21):
  - the strip vote fell to **0/16**;
  - A1 recovered in **4/4** cells;
  - translate still recovered (12/12).

  The harness tells the kernels apart, and the translate variant does not depend on the D22 digest.
- **The measurement environment was checked, not assumed.** The isolated-world truth control failed
  the first full run, which is how the GPU→CPU backing switch was found. The 0/40 at N = 21 from that
  run is an artifact and is not reported as a result.
- **The budget prototype's first run measured nothing.** Puppeteer evaluates with `userGesture: true`,
  so "reset on `userActivation.isActive`" never limited anything. The budget now refills only on a
  new trusted `pointerdown` or `keydown`, and the rerun above blanks as designed.

## Limits

- One machine (Apple silicon, macOS), one Chrome build, headless. The attack depends only on
  determinism within one browser, so other machines should behave the same; that has not been
  measured.
- Synthetic content. Real FingerprintJS content is smaller (≈ 27,000 pixels against our 200,000), so
  fewer pixels need to come out right and fewer canvases should suffice; not measured.
- The prototypes are in-page re-implementations, not shim builds. The extracted "shipped" kernel
  behaves like the real extension (N = 21: 10/10 against 40/40; single reads ≈ 25,000 pixels wrong
  in both).
- Not measured:
  - a cross-document read budget run from the service worker (reasoning only; see D56);
  - fuzzy matching (N = 9 already leaves only ≈ 80 pixels wrong, which any nearest-neighbour matcher
    would join);
  - `toDataURL`, which uses the same key as `getImageData`;
  - WebGL `readPixels`, which is keyed on its own region and is likely open to the same attack.
- The paper's own recommendations are not available to us:
  - non-deterministic per-read noise reopens averaging and is itself a fingerprint (D2);
  - GAN noise that mimics real rendering variation is future research;
  - API monitoring is detection, not protection.
